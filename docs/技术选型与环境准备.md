# 技术选型与环境准备

确认日期：2026年11月9日。

## 决策

Godot 4.x 稳定标准版与带类型 GDScript 为主要开发环境，静态定义采用 Resource，游戏运行使用内存 WorldState，本地持久化采用 SQLite。暂不使用 MySQL，不默认引入 C++。VS Code 为代码编辑器，Godot 编辑器负责场景、地图、动画与运行调试。

优先完成1主城、3区域、3兵种、最多120个战斗实体的 MVP。性能预算是验收目标，不是现有性能承诺。先优化算法和数据访问，经过 Profiler 测量仍不达标的模块才评估 C++ GDExtension。

## 对旧设计的变更

本文件优先于 docs/archive 中的旧设计。

旧文档的 JSON 主存档改为 SQLite；旧 JSON Schema 和示例仅保留为历史数据模型参考，不再作为生产存档契约。MVP 不加入专用军粮、多城物流、骑兵或完整攻城器械。

Resource 保存建筑、配方、兵种、科技、任务等静态定义；数据库只保存存档槽及动态世界状态。不把图片、音频或节点引用放进数据库。

## SQLite 接入验收

Godot 不应被假定已经内置本项目所需的 SQLite 接口。引入第三方 SQLite 扩展前，必须核对维护状态、许可证、锁定版本和 Windows x86_64 预编译包，以及与选定 Godot 版本的兼容性；验证通过后记录来源与版本。

首个验证项目仅需实现创建库、建表、插入、读取、事务回滚和导出后运行。若插件未通过验证，不直接扩写整套游戏数据库，也不静默改回 MySQL。

游戏系统只访问 SaveRepository 接口，不直接执行 SQL。数据库实现由 SQLiteSaveRepository 承担。实时移动、攻击和资源展示读取内存状态，不能逐帧查询数据库。

## 数据库基本设计

建议先使用以下表，具体DDL在存档阶段实施：

- schema_migrations：数据库结构版本及执行记录。
- save_slots：存档ID、内容版本、游戏版本、保存时间、快照版本。
- world_snapshots：save_id、完整动态DTO快照和校验值，按保存事务整体替换。

MVP 可先将动态DTO以JSON文本存入SQLite快照表，获得事务、存档槽和迁移能力；JSON此时是数据库内部编码，不是独立主存档文件。确实需要独立查询实体时，再迁移为 towns、buildings、inventories、armies 等关联表，不同时维护两套权威状态。

保存先在逻辑步边界捕获不可变快照，再用一个事务写入。读取先验证结构版本、内容ID和人口库存守恒，在临时WorldState构建成功后才替换当前世界。任何失败保留原存档与当前世界。

不要在数据库打开时仅复制主文件作为备份；使用插件支持的SQLite备份能力，或关闭连接并确认写入完成后复制。并发写入和后台保存先延期，MVP 单连接串行操作。
