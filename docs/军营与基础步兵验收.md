# 军营与基础步兵验收

## 本步范围与兵源

用户选择从城镇空闲劳动力征募，训练及现役都占用该人口。总人口不因征募或训练完成改变：30 = 被抚养6 + 施工 + 生产 + 军职 + 空闲。征募即预留5人，训练完成只切换状态，不再次扣人；生产和施工分配都检查相同余额。

此步提供军营、步兵类别的民兵兵种、5人批次训练、编额、军需与存档。部队是管理数据，尚无地图上的作战单位、自动战斗或军团命令。所有参数待平衡。

## 静态配置

| 内容 | 稳定ID | 初始参数 |
|---|---|---|
| 军营 | b_barracks | 3×3普通陆地，木30/石10/金30，施工80工作 |
| 民兵步兵 | u_infantry | category=infantry，城镇兵源，每批5人 |
| 招募 | recruit_cost | 每批金币50、木材5，一次支付 |
| 训练 | train_work | 每批60战略秒，不受施工工人数影响 |
| 军营编额 | barracks_capacity | 10人，含训练与现役；同时最多一批训练 |
| 额外军粮 | food_per_day | 每军职1/日，训练和现役均计 |
| 军饷 | wage_per_day | 每军职1金币/日，训练和现役均计 |

unit_definition.gd和game/data/units/infantry.tres保存兵种静态分类与费用；barracks.tres保存建筑静态参数，按Godot原生格式保留首行。动态存档只保存稳定unit_id，后续再添加远程、骑兵、攻城和辅助，不在本步一次铺开。

军营不设生产岗位，兵员自身训练，无需训练教官或生产工人。2名施工工人下建营80秒，4倍速约20秒；训练60秒，4倍速约15秒。每座军营独立训练，不同军营可同时训练，但兵源共用。

## 招募与开销

招募前依次检查：选中已完工军营、该营无训练批次、编额足够、全镇空闲至少5、资源够支付。失败不扣钱、不占人、不增加部队编号或成功回执。每次操作用稳定命令ID，同一成功请求重试只返回原批次，不重复扣费或预留兵源。

每战略秒先推进既有军队，再推进生产/施工，最后日结。训练每秒+1工作，完成后state从training切换ready；完成时保留维护信用，不重复征募。暂停冻结全部工作和开销累计，倍速仅推进战略时钟。

每批持有独立整数ration_credit和wage_credit：

    ration_credit += 人数 × 每人每日军粮
    wage_credit += 人数 × 每人每日军饷
    日结应付 = floor(credit / 120)
    日结后 credit %= 120

当日只服役一秒不会扣整日费用，零头跨日和存档保留。训练/现役采用相同维护率；不能靠读档或完成训练重置开销。

军粮是额外训练/服役补给。原30人口基础口粮15包括服役居民的基本生活粮，仍按原规则消费；军职每人每日额外粮1。该阶段税基仍为总人口30，不因兵员服役额外降低。此为首版简化，后续经济改动需单独验收。

日结顺序：基础口粮收获/消耗 → 材料入库 → 税收与居民满意度 → 军粮与军饷 → 完成日标记。军队实付分别取min(库存,应付)，不出现负库存。军粮短缺不直接改变居民满意度；下一日若基础口粮不足，仍按既有居民缺粮规则处理。

不足部分只记本日food_shortage/wage_shortage，不累计债务、不删除兵员、不触发叛乱、逃兵或战斗惩罚。之后接入军队士气时再明确后果，避免首版突然损失玩家部队。

## 界面与生命周期边界

右侧新增建军营按钮。地图选中军营后，详情显示编额、招募费用、训练时长及每批状态/百分比，招募按钮随条件启用或禁用；总览分开显示现役、训练和城镇劳动力占用。部队完成训练后以“现役”管理状态表示，并不意味着已有作战场景。

日结摘要与军事账单列出军粮/军饷。粮食明细明确区分基础口粮后余额、再付军粮和军需后余粮，避免历史基础口粮账单余额被误认为最终库存。

军营有关联训练或现役批次时禁止拆除；无部队军营沿用原取消/拆除规则。本阶段无取消训练、退役解散、补员、军团、出征、装备或战斗，后续逐步实现。没有部队时军事账单仍可保存零开销，但界面隐藏无关提示。

## 存档v10

新增根字段troops、recruit_commands、next_troop_id、last_army_ledger。批次示例：

```json
{
  "id": "troop_000001", "unit_id": "u_infantry",
  "barracks_id": "building_000002", "source": "town", "count": 5,
  "state": "training", "work_done": 30, "work_required": 60,
  "ration_credit": 150, "wage_credit": 150
}
```

recruit_commands中的成功回执包含troop_id、barracks_id、unit_id、source、count。下一ID不复用；当前最多64个批次，每营10人，正常初始人口/劳动力实际使可征募数更低。

军事账单示例（与基础口粮、税收后的同日余额衔接）：

```json
{
  "day": 2, "food_needed": 5, "food_used": 5, "food_shortage": 0,
  "wage_needed": 5, "wage_paid": 5, "wage_shortage": 0,
  "food_before": 149, "food_after": 144,
  "gold_before": 259, "gold_after": 254
}
```

Army.restore_world先校验临时数据：兵种与来源白名单、稳定ID/计数器、人数批次、训练状态与进度、整数开销范围、军营必须存在且已完工、每营编额和训练数、每个批次唯一招募回执、同日账单算术与基础口粮/税收连接、总体人口不超配，全部通过后才替换新世界的军队字段。

SQLite结构仍v2。旧v1至v9默认无军队、下一部队ID为1、无军事历史，不改变库存/建筑/满意度/岗位，不追溯军需费用。修改兵种批次、来源或维护参数时需明确版本迁移，不能使旧批次或整数信用静默失效。

## 模块与验证

army_service.gd负责人数与军营统计、招募预检/原子命令、时间推进、按时维护和存档校验；world_state连接人口与日结；strategic_clock固定步调用；removal_service保护有关联部队的军营；world_prototype只协调详情按钮与状态显示。

army_test覆盖：军营工地禁止招募、成本/兵源/失败原子性、成功命令重放/冲突、在训/现役占用一致、暂停倍速、50%中途数据库重开、第二批与每营编额、完整与部分服役日开销、同日不重复、多营并训、兵源不足、最后一秒开销零头、不足不负库存或丢兵、坏引用/来源/人数/信用/回执/账单/人口超配拒绝、v9迁移、真实军营按钮/进度/读档和军粮后的最终余额。

完整构建16项测试及debug/release共40项独立进程检查。新增army写进程在第110秒保存50%训练及5名预留兵员；读进程续130秒到第3日，验证现役5、空闲17、粮144、金254、当日军需5/5，旧招募命令不重复扣费，军事账单与批次可再次保存重开。日志E:/playproject/builds/army-build.log，不提交个人数据库或exe。

手动测试见开发测试指南步骤十六。自动场景检查不能替代全部人工布局与操作验收。

实际窗口补充检查：军营工地的招募按钮禁用，完工后启用；一次招募后显示编额5/10、步兵5人训练0%，按钮随即禁用并说明该营已有训练批次。已把编额、费用、训练时长分行，避免数字断行。临时画面检查未保存测试进度。
